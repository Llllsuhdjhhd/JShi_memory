# 10 总体设计与主体模型

> 范围：10–209（子文档可用 20–200）｜状态：草稿

## 1. 改动内容

本部分是全部改造的总纲，具体改动按章节拆分：

- **主体模型**：确立"只有一个主体：匠石"，删除 REMS 原有的多角色 / 多用户（UserMode SINGLE/MULTI）概念
- **输入模型（回归简单）**：输入 = 经历原文 + `subject_id` + 可选 `object_ids` + `source_ids` + 时间，不做内容分类（见 000 肃清说明）
- **流程拆分**：把 `REMSPipeline.ingest` 的单线流程拆成两个独立端口——**记忆（写入）**与**回忆（读取，先阙如）**
- **范围裁剪**：只删除抽象（详见 1210、1410）；**做梦与回忆的代码保留不动**（本次不开发，不删除、不修改）
- **接入契约**：对齐 JShi 09 的 MemoryBackendPort（`ingest_batch → BackendIngestResult`，含 `stored_marks` 供 30 侧推进游标；`recall → BackendRecallResult`，本轮占位不动）

## 2. 原因

对应匠石的需求约束：

1. 主体只有一个匠石——REMS 的多主体 / 多用户模式与匠石架构冲突；
2. 回忆与记忆是两件独立的事——现状把两者糅合进同一条 ingest 线，必须拆开；
3. 对象由输入提供——输入带 01 `object_ids`，角色 / 对象管理基于 01 对象体系；
4. 主体恒在——`subject_id` 显式（恒为当前匠石），且 `subject_id` 绝不放入 `object_id`（匠石边界，见 000）；
5. 主体记忆（无对象）合法——`object_ids` 可为空，封存时角色列表可只含主体；
6. 事件封装完全参照现状——但事件长度、强制封装细节待讨论（见 610）；
7. 角色系统完全参照现状——含情感（8 维情绪、EMA、白描遗忘）；
8–9. 回忆、做梦本次不开发，但**代码保留不动**——这两块独立于当前改造，后续需要单独认真设计（接口、数据结构、与记忆侧的关系都未定），本轮不删除、不修改，保留原样作为后续设计输入；
10. 抽象删除（本轮唯一删除项）；
11. 无关内容尽量删除——仅限与抽象相关的代码。

## 3. 目标

- 单主体记忆后端：输入（经历原文 + `subject_id` + 可选 `object_ids` + `source_ids` + 时间）→ 事件 / 对象档案持久化；
- 记忆 / 回忆两个独立端口，互不耦合（回忆代码保留，但不参与记忆写入路径）；
- 只删除抽象相关代码；做梦、回忆代码原样保留；测试基线不回归。

## 4. 与其他模块的关系

- 000 肃清说明：输入模型回归简单（2XX 弃用），本总纲不再展开输入协议；
- 410 角色系统 / 610 事件封装 / 810 存储与 Schema：记忆端口的实现块；
- 1010 回忆 / 1210 做梦与抽象：预留或删除，划定边界；
- 1410 清理清单：把"删除无关内容"落到具体文件；
- 1610 测试与验收：每步改造的回归标准。

## 5. 预留的功能

- MemoryBackendPort 双端口形状（`ingest_batch` / `recall`）；
- schema 的 `subject_id` 作用域（当前恒为单个主体值，为将来每个匠石独立实例预留）；
- 回忆、做梦的现有代码原样保留（独立块，后续单独设计，见 1010）；
- 抽象删除后的回补路径见 1210。

## 6. 待讨论问题

- 事件长度与强制封装细节（→ 610）；
- `source_ids`（来源链：事实 / 活动 / 认知 id）的语义与落库（→ 610、810）；
- 无 id 的对象不进输入（000 已定），无需候选 / 暂存机制；
- 信念修正 / 墓碑（tombstone）是否保留（属记忆维护范畴，待定）；
- 记忆写入时是否仍写向量索引（回忆阙如时可不写，未来需重建 → 810）。
- 拆分后记忆写入路径是否继续调用现有的回忆代码（"回忆不动"与"端口拆分"的交点 → 1010）。
