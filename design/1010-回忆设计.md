# 1010 回忆设计（RAG 选型与检索管线）

> 范围：1010–1209（子文档可用 1020–1200）｜状态：已确认（定稿）

## 1. 定位

- 回忆端口：`recall(subject_id, query, *, object_id=None, level=1, limit=None, anchor_event_ids=()) -> tuple[RecalledFragment, ...]`；
- **只读 + 记忆恢复 + 可选观测**：recall 不新增记忆单元（与**已删的抽象链 recall_log 无关**）；命中事件强化遗忘因子（回忆加强记忆）。可设 `recall_trace_enabled` 把本次**输入 + 命中条目**记入 `recall_traces`（仅观测，不触发抽象）；
- **决定（2026-08-23）**：**不保留旧回忆模块**（RecallService、tri_band、retrieval backends、BM25、Tier-1 等），完全按本方案重写；**做梦仍不动**；
- **决定（2026-09-01）**：引入「说话人归属 + 软纠偏」——`interlocutor`（说话/互动对象）与 `objects`（泛提及对象）**分成两个属性**；召回对每条命中按 `interlocutor` 做**有界软纠偏**（见 §8.3），并用 `recall_traces` 落观测轨迹。

## 2. RAG 技术盘点与选型（适合本项目）

### 2.1 向量嵌入：BGE-M3（推荐）

- **BGE-M3**：dense（稠密）+ sparse（词法）+ multi-vector（ColBERT 细粒度）三合一，多语言（含中文强），支持 8192 token；一套模型直接给出"语义 + 词法 + 细粒度"三路信号，天然支撑混合检索，替代"TriBandEncoder + BM25"的复杂组合；
- 备选：`bge-large-zh-v1.5`（纯 dense，轻量）、`Qwen3-Embedding`（更强但更重）。
- **项目特有信号不丢**：现有 tri_band 的 emo 频段（情感匹配）与 ent 频段（对象锚定）是领域信号，建议保留为附加通道（过滤/调制层面），BGE-M3 只接管 act 语义频段。

### 2.1.1 情感检索（emo）的现状与落地

- **现状**：通用 RAG 没有把"情感"当一等检索维度的成熟方案；相关能力集中在垂直领域研究——情感分类 / 情感嵌入（EmoBERTa、GoEmotions、中文情感语料 CEM / ChnSentiCorp）、情感空间匹配（valence-arousal 二维 / 三维坐标按距离检索）、情感条件检索（共情对话、音乐推荐）。
- **可落地的做法（本项目）**：事件已有 8 维主体情感 → 作为**低维附加向量通道**（8 维 → 低维嵌入，或直接用 valence / arousal 距离）+ 查询侧意图（emotion 类）激活情感匹配 + valence 距离调制；
- **定位**：emo 是**调制 / 辅助信号，不作主导召回**——情感相似对"记得当时的感觉"这类查询有帮助，但单独靠它召回不可靠。

### 2.2 混合召回 + 融合（行业标准，已有基础）

- 混合检索（dense + sparse + reranker）是生产事实标准（BEIR/MTEB 上比纯 dense 高 5–15 nDCG@10）；
- 本项目已具备：RRF 融合、BM25、recency、意图分类（fact / entity / emotion 软混合）、遗忘因子调制——**保留并增强**；
- 新增：对象路（object_id 过滤 + 对象时间线反查事件）、锚点路（anchor_event_ids + 80/20 分裂前缀链展开）、情感路（valence 匹配，可选）。

### 2.3 精排：bge-reranker-v2-m3（推荐）

- Cross-encoder 重排 top-N（如 60 → 20），对短查询与长段落匹配提升明显（SemEval 三阶段方案验证）；
- 本地跑（CPU 慢 / GPU 快）或走 API，按部署条件定；
- 精排输入建议带"摘要 + 对象名 + 情感标签"上下文，不直接用长原文（成本与精度平衡）。

### 2.4 上下文增强（零成本，利用现有摘要）

- 事件已有 L1–L10 摘要——检索文本 = **L1 摘要 + 对象名 + 情感标签**拼接（对齐 A-Mem "富化嵌入"与 Contextual Retrieval 思路），原文 content_raw 只在最终展示；相当于内置"上下文检索"；
- HyDE（为短查询生成假设性事件文本再检索）：可选，成本高，默认不做。

### 2.5 知识类记忆（二期可选）

- `content_type=knowledge`（学到的知识）多跳关系检索：可选 **LightRAG / GraphRAG**（对象作节点）；
- 本阶段不做——对象体系在 01 侧，记忆后端先做事件级 RAG，图谱能力留给后续。

### 2.6 个人记忆系统的借鉴（不照搬）

- Generative Agents / somnigraph：**按最后访问时间衰减 + 访问加热**（reheat）——与我们的"遗忘因子 + 回忆恢复"一致，已具备；
- MemGPT / Letta：工作记忆 + 归档记忆分层——我们的事件 + 摘要档位 + 未完成缓冲已是类似结构；
- Mem0 / Zep 的写入期 LLM 抽取：与"不抽取、不建档"冲突，不采用。

## 3. 检索管线（启用方案）

```text
recall(subject_id, query, *, object_id, level, limit, anchor_event_ids)
  ├─ 1. 查询理解：query 压缩/重写（现有）+ 意图分类（fact/entity/emotion 软混合）
  ├─ 2. 候选生成（多路并集，subject_id 作用域）：
  │     ├─ 语义路：BGE-M3 dense（L1 摘要 + 对象名 + 情感标签）
  │     ├─ 词法路：BGE-M3 sparse / BM25
  │     ├─ 对象路：object_id 过滤 + 对象时间线反查
  │     ├─ 时间路：recency（最近窗口）
  │     ├─ 情感路：valence 匹配（可选）
  │     ├─ 锚点路：anchor_event_ids + 分裂前缀链展开
  │     └─ 活跃池：Tier-1 A-Res 预过滤（启用时恢复）
  ├─ 3. 融合排序：RRF + 遗忘因子/时间衰减 + 情感调制 + **对象归属软纠偏**（× intermediate
  │        aff_i，仅焦点对象明确且条目有 interlocutor 时非 1.0；见 §8.3；无 abstract_coverage）
  ├─ 4. 精排：bge-reranker-v2-m3 对 top-N 重排
  ├─ 5. 预算与档位：level + physical_redline；role-aware 摘要档位（L1–L10）
  ├─ 6. 组装 RecalledFragment（event_id / text=原文 / kind / object_id / interlocutor / source_ids / score / summary_level）
  └─ 7. 记忆恢复：命中事件强化遗忘因子（唯一记忆写操作）+ 可选写 recall_traces（观测，非记忆写）
```

## 8. 返回格式

### 8.1 原系统（REMS3 RecallService）的返回模式

- `RecallBlock.items: list[RecallItem]`；`RecallItem = {event_id, content, score, summary_level}`；
- **`content` 是按摘要档位（L1 / mid / ultra 等）选出的摘要文本，不是原文**（`_role_aware_pick_summary` 产物）；
- 整体包在 `ContextPackage(recall_block, shadow, current_input)` 里，`assemble()` 拼成带 `[历史回忆] / [残影缓冲] / [当前输入]` 标题的文本供 LLM 使用。

### 8.2 新格式（RecalledFragment，建议扩展）

```python
class RecalledFragment:
    event_id: str
    text: str            # 原文（content_raw），溯源用（契约字段）
    content: str         # 按 summary_level 选出的摘要文本，供预算 / 组装（建议新增，对齐原 RecallItem.content）
    kind: str | None
    object_id: str | None           # 泛提及/主对象（实体路用）
    interlocutor: str | None        # 说话/互动对象（驱动软纠偏；与 object_id 区分，见 §8.3）
    source_ids: list[str]
    score: float
    summary_level: str | None
```

- 回忆端口只返回片段列表（`tuple[RecalledFragment, ...]`）；**残影 / 未完成不跨端口**（内部缓冲）；
- `text=原文` 满足契约溯源；`content=档位摘要` 保留原系统"按预算取档位文本"的可用性。

### 8.3 说话人归属（interlocutor）与回忆轨迹（recall_traces）＋软纠偏

> 与已删除的抽象 `recall_log`（频繁子集挖掘触发）**完全无关**。本节是"防串线"的可观测 + 有界软纠偏。

**两个对象属性要分开**（易混淆，务必区分）：

| 属性 | 含义 | 来源 | 用途 |
|---|---|---|---|
| `objects` / `mentioned_objects` | 文本中**提及/涉及**的所有对象（含没说话、没出现） | Jshi `MemoryExperience.objects` | 实体路 / 对象过滤 |
| `interlocutor` | 本段**说话/互动对象**（主体对话的对象） | Jshi `ExperienceSegment.actor_object_id` | **驱动软纠偏**、防串线 |

**落盘**：ingest 时按子段（`sub_segments`）把 `interlocutor` 写入事件（`recall_metadata.interlocutor`）；
主体自述 / 系统段为 `None`，天然中性。Jshi 侧在 `memorycontrol.build_batch` 里把 `segment.actor_object_id`
作为 `interlocutor` 传入（`actor_object_id` 是外部对象 id，不与主体混用）。

**recall_traces（观测）**：每次 `recall` 落一行，记**输入**（query / object_id / level / limit / anchor_event_ids / created_at）
与**命中条目**（event_id / object_id / **interlocutor** / score / summary_level / source_ids / text / content）。
只作观测，不参与抽象、不影响召回结果。配置：`REMS_RECALL_TRACE_ENABLED`（默认 true）、`REMS_RECALL_TRACE_MAX_ITEMS`。

**有界软纠偏（防串线）**：打分时对每条命中乘 `aff_i`：

```
aff_i =
    1.0                                    # 未启用 / 无焦点对象 / 条目无 interlocutor（退化为纯主题）
    recall_object_affinity_boost (1.15)    # 条目.interlocutor == 焦点对象
    recall_object_affinity_penalty (0.90)  # 条目.interlocutor != 焦点对象
```

- **焦点对象** = recall 的 `object_id`（Jshi 侧传当前说话者 `speaker.object_id`）；
- **有界、不硬删、不过度**：±0.15 只影响"主题相关近似时谁排前"，**不会删掉不同对象但强相关的记忆**；
  也不会因为缺归属就乱纠偏（缺一方即乘 1.0）；
- 配置：`REMS_RECALL_OBJECT_AFFINITY_ENABLED`、`..._BOOST`、`..._PENALTY`。

**验收**：给焦点 `OBJ-LUX` 召回时，`OBJ-LUX` 记忆排前、`OBJ-LUGUANG` 强相关记忆仍返回；`recall_traces`
每条能核对 `interlocutor` 归属。

### 8.4 人物肖像（per-object 10 级渐进人物摘要 + 记忆疲态）

对一个人物/对象的综合性描述。**一次记忆落位涉及多个对象时，为每个对象各生成一条人物摘要**
（主体对该对象的记忆），汇入各自独立缓冲与画像——每人一份、彼此独立。

**等级化**（`PortraitService.compute_level_budgets`，确定性）：
```
L1 = max(portrait_magic_num(100), 总长 / portrait_growth^(max_levels-1))   # 取较长，保最短级有效
Lk = L1 * portrait_growth^(k-1)                                            # 每级是上一级 2 倍
某级预算 > 总长 → 暂停（不再往上加），已保留各级原长度；最多 portrait_max_levels(10) 级
```
- `总长` = 该对象累计的人物摘要字数（**增量累积，不每次重算**）；`compression_ratio = 总长 / 最长一级字数`。
- 触发：某对象「待并入」人物摘要累计字数 ≥ `context_window / portrait_trigger_divisor(600)` 时执行肖像动作。

**两种压缩/组建方式**（`portrait_compose_mode`）：
- `incremental`：用已有肖像的最长级 + 新摘要集 → 模型压缩成新多级（内容多时不整包重建）；
- `full`：用该对象**所有**人物摘要 → 重建多级；
- `auto`（默认）：当累计总长 ≤ `context_window × portrait_full_mode_context_ratio`（默认 1/6 上下文）时用
  `full`（所有摘要），否则用 `incremental`——内容在安全范围内才整包重建。

**记忆疲态**（分两个值，**不能共用一个**）：
| 目标 | 依赖 | 值 |
|---|---|---|
| 事件（召回） | 仅整体记忆负担 | `event_fatigue` → 乘进 `effective_factor`（与遗忘率协同） |
| 人物肖像摘要 | 整体 + 对象负担 | `portrait_fatigue` → 集合级 `apply_fatigue`（期望可见 ≈ fatigue）+ 偶然性 |

- 疲态默认 `1.0`（无遗忘）；`<1` 时按概率让部分摘要/事件概率不可见，**保留偶然性**（低权重仍可能可见，非硬切）；
- 事件疲态与遗忘率**协同**：`effective = event_fatigue × forgetting_factor × 时间衰减`（`recall._effective_factor`）。

**暴露**：`REMSPipeline.portrait(subject_id, object_id)`（`MemoryBackendPort` 端口新增 `portrait`）。
**落库**：`object_portraits` + `portrait_summaries`；模型 `ObjectPortrait` / `PortraitLevelInfo` / `PendingPortraitSummary`。

### 8.5 回忆预算管理（Recall Budget Management）

- **预算** = 本次回忆的总字数，与回忆等级相关。回忆分 `recall_level_count`（默认 6）级，各级字数递增：
  `L1=最短=recall_magic_num(100)`，逐级 ×`recall_level_growth(2)`，`L{count}=最长`（L6=3200）。
  **项目统一**：`L1=最简/最短`，高级别=更详细/更长（与人物肖像口径一致）。
- **分配**（`RecallBudgetManager.allocate`，贪心）：回忆条目按评分排序（含对话人的人物肖像，优先级更高），
  **能装最高级就装最高级，装不下下降级，再装不下丢弃**；实际展示字数 = `min(档位上限, 内容长度)`。
- **总约束**：拼装总字数 ≤ `recall_budget_chars`（0 => `physical_redline`）。`recall()` 返回时应用；另有
  `assemble_recall_block(...)` 返回预算受限的块（条目+等级+总长）。
- **肖像同场**：`apply_recall_budget` 里把 `object_id`（对话人）的人物肖像包装成一个回忆条目（`score` 高，优先），
  与事件条目一起分级/占预算。

## 9. 部署（已定：本地 + 插拔式）

### 9.1 插拔式架构

- **EmbeddingProvider**（接口）：`embed_documents / embed_query`；本地实现（bge-base-zh / BGE-M3），可换 API 或量化版；
- **RerankerProvider**（接口）：`rerank(query, candidates) -> scores`；本地实现（bge-reranker-v2-m3）或 None（纯 RRF）；
- **VectorStore**（接口）：`upsert / search / delete`；Qdrant 本地模式（默认）/ 远程 / 内存（测试）；
- 配置选择实现（embedding.provider / reranker.enabled / storage.qdrant_url），运行期替换不影响管线。

- **结论：可以**。个人记忆规模（数千条事件）对检索压力很小。
- **模型资源**：
  - BGE-M3（560M，约 2.3GB）CPU 可跑：全量索引数千条事件约几分钟到几十分钟，查询时编码 + 检索 + 重排约秒级；
  - 普通电脑（8–16GB 内存）建议 `bge-base-zh-v1.5`（约 400MB）或 BGE-M3 用 int8 量化（ONNX），内存占用 0.5–2GB；
  - reranker `bge-reranker-v2-m3`（568M）CPU 慢，无 GPU 时可关（纯 RRF）或缩小 top-N。
- **向量存储**：Qdrant 用**本地模式**（`qdrant-client` path= 本地目录，无需 docker / 服务器；测试已用 `:memory:`，本地模式同理）。
- **推荐配置**：小模型（bge-base-zh）+ 本地 Qdrant + reranker 可选，普通电脑无压力；BGE-M3 + reranker 需 16GB 内存或 GPU 更顺。

- `tests/unit` 基线不回归。
