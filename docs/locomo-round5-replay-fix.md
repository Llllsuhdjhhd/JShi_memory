## 实现与重复原因

轻量事件闭合即存，不生成摘要、情绪和角色分析；默认按原经历发生满 90、365、1095 天提炼。第一次原样拼小事件正文作为 L0，后续读取前阶段 L1。各阶段 L1 默认保留三分之一，可独立配置。发布成功才隐藏来源，底层及关联保留，向下自动取回暂不实现。

重复原因定位在投递确认：相邻 JShi 的 `_consumed_sequence` 在存在封存回执时只推进到最远被封存段；后续段可能已进入记忆缓冲，却再次投递。记忆侧此前没有区分这类部分重投，最后强制保存时又形成包含旧事件正文的较长事件。

本次在记忆侧为每个原始断句记录主体、稳定来源、原文位置和内容对应的标识，同时检查未闭合缓冲及已封存事件。超长断句分片也有独立稳定标识。相同来源中不同位置的重复语句、不同来源中的相同表述都保留；没有稳定来源的旧输入不猜测去重。本次没有修改相邻 JShi 项目，也没有自动清洗旧库。

## 进一步定位：长度修复为什么会丢细节

q47 的 API 原始输出最初包含完整支持者名单。因为摘要超长，既有长度修复让模型返回完整事实句，再由程序按返回顺序装入字符预算。修复输出中，领养计划和较长图片描述排在前面，支持者名单排在后面；前面的内容占满预算，后面的完整事实句被舍弃。

因此不能仅归因于 Flash 没读懂原文：它在初次生成和修复事实中都写出了名单。当前事实排序与按序装入规则，同样造成了损失。代码没有把某句话从中间截断，但会整句舍弃，甚至让一个被聚合的小事件在 L1 中没有任何信息。这是当前尚未解决的质量限制。

建议下一步保持当前时间阶段和来源结构，优先改提炼质量：为每个来源小事件分配保留空间，先保留具体人名、名单成员、数量、行为和时间，再使用余量保留叙述；检查每个来源是否有代表事实，避免整件事情消失。针对检索，则检查问题中的目标行为、事件实例及时间约束，避免同主题的另一次事件替代答案。不能只继续提高压缩率或更换模型来解释全部问题。本次未擅自加入新的事实层或实现向下取回。
