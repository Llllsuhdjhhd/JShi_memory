# 匠石记忆系统：经验形成与经验召回框架设计

## 1. 文档目的

本文定义匠石记忆系统中，在现有 **Event Memory** 基础上进一步形成长期经验，并在需要时重新调用这些经验的总体框架。

本设计重点解决两个问题：

1. **经验如何累积形成**
2. **已经形成的经验如何被召回并参与当前行为**

当前阶段只确定系统结构、信息流和模块边界，不提前规定复杂的经验形成算法、合并算法、冲突处理算法或在线训练机制。

系统原则是：

> **Event 保存具体经历；Experience 保存长期经历沉淀出的认识。**

同时：

> **经验的形成与经验的召回是两个独立阶段。**

---

# 2. 基础层：Event Memory

Event 仍然是整个长期记忆系统的基础。

Event 表示匠石已经发生过的一段相对独立、具有自然语义边界的经验，包括：

- 与某个人发生的互动；
- 在某个环境中的经历；
- 对物体、设备、商品的使用；
- 某种反复出现的情境；
- 被告知、观察到、思考过的内容；
- 其他能够形成经验单元的经历。

Event 保存的是：

> **“发生过什么。”**

Experience 不替代 Event，也不修改 Event 的定义。

长期经验必须能够追溯到真实的 Event。

---

# 3. 现有 Event Recall 的扩展

现有 Event Recall 主流程保持不变。

当前已经存在的召回机制继续承担第一阶段候选检索，例如：

- embedding / semantic recall；
- lexical recall；
- object recall；
- time recall；
- anchor recall；
- RRF 等现有融合与排序机制。

总体结构为：

```text
Event 全库
    ↓
现有多路 Recall
    ↓
候选 Event
    ↓
[可选 Jev 精筛]
    ↓
预算装配
    ↓
交给上层模型
```

## 3.1 Jev 的定位

Jev 不替代现有 Recall。

它只作为：

> **候选已经被召回之后的可选精筛器。**

因此：

```text
jev_enabled = false
```

可以作为默认配置。

只有在后续实验确认 Jev 对召回质量有明显提升时，才开启这一层。

其基本思想为：

```text
大规模记忆库
    ↓
低成本粗召回
    ↓
少量候选
    ↓
Jev 精判断
```

禁止直接让 Jev 扫描整个 Event 数据库。

---

# 4. 长期经验形成的总体结构

长期经验形成分为两个主要方向：

```text
                     Event
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
      人物路径                 通用经验形成路径
          │                         │
    白描 / 肖像等             Dream / 回溯 / 归纳
          │                         │
          ▼                         ▼
      人物记忆                  Experience
```

两条路径不是互斥关系。

特别是：

> **人物既拥有专门的人物记忆形成机制，也参与通用经验形成机制。**

---

# 5. 人物长期记忆

人物是匠石未来长期交互中最重要的一类对象，因此保留独立路径。

人物具有天然稳定标识：

```text
person_id / object_id
```

因此人物相关长期信息可以稳定地挂载到对应人物之下。

## 5.1 第一条来源：人物直接积累

Event 封存以后，可以通过已有的人物处理过程形成：

- 白描；
- 人物事实；
- 人物肖像；
- 其他与人物长期认识有关的信息。

例如：

```text
Event
  ↓
识别人物
  ↓
白描 / 人物信息提取
  ↓
人物长期记忆
```

这是一条天然、直接、低歧义的路径。

---

## 5.2 第二条来源：通用经验形成

人物不会被排除在一般经验归纳之外。

例如多个 Event：

```text
E1：小米专注工作时，对模糊问题回应很短。
E2：另一次工作时，被连续询问后表现出明显不耐烦。
E3：简短明确的事务提醒没有造成明显影响。
```

经过 Dream、回溯、归纳等过程以后，可能形成：

> 小米在高度专注时通常不喜欢模糊或持续性的打断，但对简短明确的事务提醒接受程度较高。

这属于从多个经历中形成的经验。

由于经验明确涉及小米，因此可以：

```text
experience.person_id = OBJ-xiaomi
```

并挂到该人物的长期记忆下面。

---

## 5.3 人物使用同一长期账本

当前设计允许两条来源最终进入同一个人物长期记忆体系：

```text
                Person Memory
                     ▲
          ┌──────────┴──────────┐
          │                     │
     白描 / 肖像            Dream形成的经验
          │                     │
      人物直接路径           通用经验路径
```

不强制人为拆成两个完全独立的数据系统。

不同来源可以通过元数据保留来源信息，例如：

```text
source_type:
    direct_person
    dream
```

但具体：

- 如何写入；
- 如何合并；
- 如何修订；
- 是否覆盖；
- 如何处理冲突；

当前阶段暂不深入设计。

第一阶段可以先由大模型进行判断。

---

# 6. 通用 Experience

除了人物以外，匠石还可能长期形成大量对世界的经验。

这些经验可能来自：

- 环境；
- 地点；
- 物体；
- 商品；
- 设备；
- 天气；
- 行为习惯；
- 反复出现的场景；
- 某些现象；
- 交流模式；
- 历史经验；
- 多个不同因素共同形成的规律。

例如：

> 雨后这个山洞深处左侧通常比入口附近湿滑得多。

或者：

> 某种设备刚出现轻微振动变化时，并不一定马上影响运行，但持续增强通常值得进一步检查。

这些内容未必存在像 `person_id` 一样天然唯一的归属对象。

因此它们进入独立的：

```text
Experience Memory
```

---

# 7. Experience 的形成

当前阶段不规定复杂的形成算法。

总体只定义为：

```text
Event
   ↓
Dream / Reflection / 回溯 / 归纳
   ↓
发现跨 Event 的某种经验
   ↓
形成 Experience
```

Dream 可以利用当前或近期 Event 作为线索，重新调用过去相关 Event，并由大模型发现其中是否存在值得长期保留的经验。

例如：

```text
今天 Event
    ↓
Recall 历史相关 Event
    ↓
共同交给大模型
    ↓
归纳是否形成长期经验
```

经验并不要求一定来自完全相同的对象。

它可以跨：

- 多个时间；
- 多个地点；
- 多个对象；
- 多个类似场景。

因此 Experience 是比单个 Event 更高层的长期认识。

---

# 8. Experience 不等于 Event 摘要

Experience 不应该退化成：

> “把多个 Event 再总结一次。”

两者语义不同。

### Event

回答：

> 我经历过什么？

例如：

> 昨晚下雨以后，我进入山洞时发现左侧石面很滑。

### Experience

回答：

> 经过过去这些经历，我逐渐形成了什么认识？

例如：

> 连续降雨以后，这个山洞深处左侧通常会比其他区域更加湿滑。

因此：

```text
Event = 经历

Experience = 经历沉淀后的认识
```

Experience 不能取代 Event。

Event 仍然保留原始证据。

---

# 9. 经验召回

经验形成以后，并不是每次全部送入上下文。

Experience 同样需要召回。

经验召回主要分成两类：

1. 人物经验召回；
2. 通用经验召回。

---

# 10. 人物经验召回

人物有天然 `person_id`。

因此当前正在与某个人互动时，可以首先直接定位：

```text
当前人物
    ↓
person_id
    ↓
该人物长期经验集合
```

人物经验数量预计远小于整个通用 Experience 库。

例如：

```text
OBJ-xiaomi
    ↓
20 / 50 / 100 / 200 条人物长期经验
```

如果数据量较小，可以直接交给 Jev 判断当前哪些内容最相关：

```text
Person Memory
    ↓
Jev
    ↓
当前最相关的人物经验
    ↓
LLM
```

因此人物召回拥有一个天然优势：

> **person_id 本身就是非常强的第一层过滤。**

是否还需要 embedding，可以根据实际数据规模决定。

---

# 11. 通用经验召回

通用 Experience 与人物不同。

随着机器人运行时间增长，通用经验可能达到：

```text
几千条
几万条
甚至更多
```

因此绝对不能：

```text
全部 Experience
    ↓
Jev
```

而应该和 Event Recall 保持同样的总体思想：

```text
Experience 全库
        ↓
embedding / lexical / 其他低成本召回
        ↓
候选 Experience
        ↓
[可选 Jev 精筛]
        ↓
当前相关 Experience
        ↓
LLM
```

也就是：

> **先找，再判断。**

Jev 永远面对有限候选，而不是整个数据库。

---

# 12. 两种经验召回路径

最终可以概括为：

```text
                     当前 Context
                          │
              ┌───────────┴───────────┐
              │                       │
              ▼                       ▼
         当前涉及人物               通用场景
              │                       │
          person_id                   │
              │                       │
              ▼                       ▼
       Person Experience       Experience 全库
              │                       │
          Jev 可选             embedding / lexical
              │                       │
              │                  候选 Experience
              │                       │
              │                   Jev 可选
              │                       │
              └───────────┬───────────┘
                          ▼
                     当前经验 Context
                          ↓
                         LLM
```

---

# 13. 系统实际上存在三类召回内容

至此，匠石未来的上下文可能来自三种不同层次：

### 1. Event Recall

> 过去具体发生过什么。

### 2. Person Experience Recall

> 长期相处以后，我对当前这个人形成了哪些认识。

### 3. General Experience Recall

> 长期生活以后，我对世界、环境、物体、现象和情境形成了哪些经验。

最终：

```text
Current Context
      +
Event Recall
      +
Person Experience
      +
General Experience
      ↓
     LLM
      ↓
理解 / 思考 / 回答 / 行为
```

但三类内容均不要求每次全部存在。

系统应该根据当前场景按需调用。

# 15. 当前已经确定的设计

目前可以认为以下原则已经基本确定：

1. **Event 仍然是基础经验单元。**
2. **Experience 不替代 Event。**
3. **经验形成和经验召回是两个独立问题。**
4. **人物拥有独立的长期记忆路径。**
5. **人物同时参与通用经验形成机制。**
6. **Dream / 回溯 / 归纳可以从多个 Event 中形成 Experience。**
7. **涉及明确人物的 Experience 可以挂到对应 person_id 下。**
8. **人物直接形成的信息与 Dream 形成的人物经验可以进入同一人物长期账本。**
9. **通用 Experience 可以独立于具体人物存在。**
10. **人物经验召回可以利用 person_id 直接缩小范围。**
11. **通用 Experience 必须先经过 embedding / lexical 等低成本粗召回。**
12. **Jev 只作为候选精筛工具，不承担全库扫描。**
13. **Event Recall 同样可以增加 Jev 精排，但默认关闭。**
14. **整个系统不依赖 Jev 才能运行。**
15. **当前阶段不引入在线训练、Fast Weights、潜变量人格模型等高成本机制。**

---

# 16. 当前暂不确定的问题

以下问题保留到后续设计，不在当前阶段提前复杂化：

### Experience 如何写入

暂时允许由大模型完成判断，不立即定义严格算法。

### 人物长期账本内部的数据结构

白描、肖像、长期经验最终是否完全统一结构，后续结合实际效果确定。

### Experience 如何更新和合并

暂不确定：

- 新增；
- 修改；
- 合并；
- 冲突；
- 遗忘；
- 置信度变化。

### Dream 的具体运行机制

当前只确定：

> Dream 可以作为经验形成的重要入口。

具体：

- 多久运行一次；
- 每次处理多少 Event；
- 如何触发历史 Recall；
- 如何控制计算资源；

以后单独设计。

### Jev 的实际效果

所有 Jev 使用点均视为：

```text
optional
```

最终是否开启，由真实测试决定。

# 17. 核心设计思想

整个框架可以浓缩成四句话：

> **Event 保存发生过的经历。**

> **Dream 等过程让大量经历逐渐沉淀成 Experience。**

> **人物因为重要且具有稳定身份，拥有专门的长期记忆入口，但仍然参与一般经验形成。**

> **真正使用记忆时，先通过低成本方法找到候选，再根据需要使用 Jev 等判断器进行进一步筛选。**

因此系统最终并不是单纯的：

```text
经历 → 保存 → 回忆
```

而逐渐形成：

```text
经历
 ↓
Event
 ↓
长期沉淀
 ↓
Experience
 ↓
未来再次遇到相关人物 / 环境 / 情境
 ↓
召回
 ↓
影响当前理解与行为
```

这使匠石的记忆不仅能够回答：

> “过去发生过什么？”

还能够逐渐回答：

> **“经过过去这些经历，我已经形成了什么认识？”**

这是 Event Memory 向长期经验系统扩展的核心目标。
