# 事件、摘要、重复封存与时间的修改方案

2026-10-16。基于正式第二轮产物和代码路径；本次只做诊断、离线复现与方案，未修改生产逻辑或重跑付费评测。

## 一、为什么摘要仍然这么长

实际使用的是摘要，不是误把事件原文交给核心：样例事件原文 7275 字符，L1 为 6048，
L2 为 4821，L3 至 L10 也均为 4821。长事件本身是 truncated 兜底封存，混有多个话题。
兜底保留原文有价值，但不能把兜底长块当作正常短事件处理。

当前配置对 7275 字符原文计算出的摘要上限实际为：L1=440、L2=220、L3=110、L4=55，
后续最低 35。EventEnrichmentSkill 仅在提示词里要求长度；解析器接收字符串并统计长度，
没有校验预算或递减关系，所以模型输出的超长、重复层级全部进库。

Recall 的 select_representation 按“在后端剩余预算中能放下的最长完整摘要”选择，
并非固定取最短一级。JShi 后端召回预算与核心 1500 字符预算并未协调，
核心又整段放入后再扣预算。三层叠加，6048 字符摘要成为唯一交付回忆。

建议：

1. 摘要结果按每级预算、实际字符数、有效递减关系校验；重复级别不算压缩成功。
2. 不合法时允许一次定向压缩修复；仍失败则保留原文和 source IDs，标记摘要无效并隔离，
   交给显式恢复流程处理，不悄悄当作正常可检索事件。原文不截断、不丢弃。
3. 核心把真实剩余预算传给回忆源，事件/对象事实先合并，再选合适档位。
   第一阶段至少要求单片段放入后不超预算；放不下则换更短有效摘要或跳过并记录原因。
   之后再优化跨事件的互补信息分配，不按目标答案指导选材。
4. 超长残影先按现有句子编号切成不重叠的源片段，再封存；若必须保留跨话题兜底块，
   明确标记并单独处理，不能让它凭词面覆盖获得普通事件的优先级。

## 二、重复不是“正常剥离”的预期，存在代码缺陷

已用确定性的录制型封存器复现，不需要 LLM：
`python scripts/reproduce_memory_sealing_issues.py`。
输入仅一句 Melanie went running.，以下两条路径均调用 seal_event 两次。
结果保存在 `runs/locomo_round2_clean/sealing_reproduction.json`。

### 搁置残影重判

新版边界解析按句子 indices 给出已完成事件，fragment.continuation_of 为 None。
`_rejudge_abandoned` 仍用旧的 continuation_of 来找旧 UC 并登记 handled。
因此先把模型划出的完整事件封存一次，却没登记原 UC 已被消费；随后兜底循环又把原 UC 封存一次。

正式跑步样例 API 审计中，边界调用 #71 只返回一个 events 分组、residual=[]，
紧接着 #72、#73 对逐字相同原文各做了一次 enrichment。
与离线复现及两条重复数据库记录一致。

### 强制保存

`_force_save_all` 先把 shadow_content + raw_input 合成一个事件封存；
随后又遍历 unclosed，把已包含在 shadow_content 中的每条 UC 再封存一次。
当只有一个 UC 且新输入为空时，就是两条完全相同事件。

### 修改要求

1. 所有封存入口统一使用“句子来源 → 已消费集合 → 剩余集合”的路径。
   重判也按 indices 认领原始句子；部分消费就仅保留未消费句子，不能简单把整条 UC 删除或再封存。
2. 强制保存按 UC/剩余输入分别封存，每个源片段一次；取消“先存全部，再逐条存”的双重路径。
3. 同一批边界分组索引应互斥；一条句子不能同时归到两条已完成事件。
4. 封存与源片段消费用一致的事务边界；数据库提交后索引任务可以重试。
   重试幂等键使用 subject + 稳定 source spans，不仅用文本哈希：不同日期确实发生两次的相同话语应能保留。
5. 不把全部历史相同文本直接删除。先按源片段判定是否同一次重复封存，保留迁移映射与审计。

## 三、排序建议

先修封存和预算两个确定性问题，再改善排序：

- 保留语义分差异，避免词面满分把不同事件全部封顶为相同分数。
- 检索结果识别“谁做了什么、哪次事件”，不能只看人物名与主题词的集合覆盖。
- 按稳定来源/内容去除同一事件的冗余表示，保证新增材料优先补充不同信息。
- 列表题比较信息互补性，而不是让同一次跑步经历连续占据多个位置。

## 四、时间必须端到端保留

### 已查到的丢失点

`REMSPipeline.ingest_batch` 将多个 MemoryExperience 合并后重新构造 memory，
没有传入 occurred_at；`_seal_memory_kwargs` 虽然会透传 memory.occurred_at，拿到的值已经为空。
正式库中 94 个事件只有 3 个 occurred_at 非空，且三条来自最后的显式残留封存。
测试回放后来校正 create_time 掩盖了部分展示问题，但创建时间不能替代真实发生时间。

当前 BufferSentence 也没有逐句来源日期字段，跨批、跨会话残影可能失去每句话的原始时间归属。
最后提示词把兜底时间显示成粗粒度“2个月前”，核心看不到能解析 yesterday/last Friday 的会话日期。

### 建议的数据契约

| 字段 | 含义与约束 |
|---|---|
| source_id + utterance/span ID | 原始发言和源片段的稳定身份 |
| statement_at | 这句话在哪个日期时间说出；保留源时区与已知精度 |
| event_time_start/end | 内容描述的事件时间，可为区间或未知 |
| time_expression | 原文里的 yesterday、last Friday 等表达 |
| time_precision / provenance | 日、月、区间、未知；直接给定或由明确表达推导 |
| recorded_at / create_time | 系统写入或封存时间，不能当作上述任一时间 |

逐句缓存、批次合并、边界切分、事件封存都保留稳定来源及 statement_at。
跨多个日期的事件保留来源范围；不以当前批次日期覆盖旧残影。
旧 occurred_at 可作兼容字段，但必须明确其语义，不能混用会话日期与事件日期。

### 时间解析与核心展示

相对时间解析以原句 statement_at 为锚点：

- 2023-07-03 说“昨天报名” → 报名日期 2023-07-02，精度为日。
- 2023-07-15 说“上周五参加会议” → 日期 2023-07-14，保留原始表达和推导依据。
- “前阵子”或缺少来源日期 → 未知/区间，不补造精确日期。

有明确规则的日期算术由程序执行；如需模型识别表达，只让它输出结构化表达与归属，
最终程序校验、计算。不把所有时间推断交给回答模型。
核心回忆同时展示绝对锚点与原句时间表达，例如：

```text
来源：Melanie，2023-07-03（原会话日期）
事实：Melanie 昨天报名陶艺课。
解析：报名日期 2023-07-02（日精度；由原会话日期减一天）。
```

展示名标注为“涉及人物”，事实主体另行明确，避免标题 Melanie 诱导把 Caroline 的愿望归给她。
精确日期应从来源恢复，不能靠把现有“2个月前”倒推成某一天。

## 五、先不把问题归结为 Flash 能力

确定性复现不调用模型仍会重复封存，因此换模型修不了这类问题。
摘要超预算反映了本次模型的约束遵循失败，也反映了程序缺少结果校验；两者都需要区分。
人物混淆、过度拒答等才适合进一步做回答模型能力对照。

建议继续用当前模型保持成本与变量稳定：先在固定记忆库上修复预算/排序问题，
再从空库验证剥离、时间与摘要校验。最后固定完全相同的实际交付回忆，
选 10～20 道失败题让更强回答模型只读复答，盲评、不重写记忆；
必要时再固定边界输入比较事件抽取，两个环节分开测。
这能判断收益来自记忆系统还是回答模型，避免先换模型后失去可解释性。

## 实施顺序与验收

1. 重复封存、源时间传递与摘要校验；离线验证单句只封存一次、部分消费无重叠且不丢句、
   重试幂等、跨会话日期保持、绝对日期解析以及摘要预算符合契约。
2. 对齐核心实际预算，在现有库做固定输入对照：q16 排名第 2 的正确事件、q116 的短正确事件应能交付；
   不能通过标准答案或题号给检索加特判。
3. 从空库重写同一历史，检查非预期重复为零、来源覆盖完整、时间不依赖 create_time 兜底，
   再跑相同评测并抽读实际回忆。
4. 在未参与调试的新题上验证，再决定是否进行模型能力对照。
