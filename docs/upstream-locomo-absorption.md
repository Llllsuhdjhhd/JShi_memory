## 候选去向诊断

上表的“第 4、7、12 项”是从已交付事件里人工回读出来的：只能看到交付了什么，看不到没交付的候选
排第几、为什么被淘汰。本轮补上这一段。

- `RecallPipeline.recall(..., candidate_sink=..., candidate_call=...)`：`_fill_budget` 每访问一条候选就追加一条
  `RecallCandidate`（`call` / `rank` / `material_type` / `event_id` / `object_id` / `score` / `selected` /
  `reason` / `representation_level` / `chars` / `budget_remaining`）。
- `REMSPipeline` 增加实例属性 `recall_candidate_sink`。JShi 核心经端口回调 `recall`，拿不到额外返回值，
  所以评测运行器在 `answer_question` 里临时挂上 sink，结束写入 `answers/<id>.json` 的
  `recall_candidates` 后清空。
- `audit_locomo_retrieval.py` 读到该字段时用 `candidate_ranks` 把证据 `dia_id` 映射回候选排名，追加
  `gold_material`（`recalled` / `delivered` / `not_recalled` / `best_rank_median` / `best_reason_counts`）。
  旧 run 没有该字段，输出保持不变。

两条边界：

1. `reason="limit"` 只说明还有候选被条数上限挡住，不代表目标材料排在第 `limit+1` 位。要拿完整排名，
   recall 时不传 `limit`，预算放不下的候选会以 `no_room` 继续记到候选结尾。
2. `recalled=false` 与 `truncated=true` 必须分开看：前者是没进候选池，后者是被上限截断，不能合并成
   同一个“没召回”。

验证：`tests/unit/test_recall_candidates.py` 8 项，覆盖三种淘汰原因、诊断不改变召回结果、多次调用
编号，以及证据材料在已交付与未交付两种情形下的排名归因。
