# 既定规则与当前执行的偏差

2026-10-16。只读审核当前实现、第二轮配置与 94 个封存事件；未修改生产代码。
用户本轮明确要求超长按上限拆分、L1 遵守压缩要求，这应作为修复约束。
历史文档含多个时期口径（80/20、按 ev_len 解交织、整条强制封存），不能把某份旧稿当作恢复依据。

## 规则与现状

| 约束 | 当前执行 | 后果 |
|---|---|---|
| 超长事件应受拆分规则约束 | 新版 `disentangle=True` 时 `BoundaryForceThresholdEvaluator.evaluate` 直接成功，不调用旧 80/20 修复 | 配置开启修复不代表本次协议真的经过修复 |
| 当前事件工作尺度为 `[900, 1800)` 字符 | `_apply_disentangle` 发现不符合 `_length_accepted` 后留回残影，不拆分 | 超长内容反复保留而非收敛到可封存长度 |
| 最终封存也应满足上限 | 物理红线、搁置重判与强制保存可直接 `seal_event`，封存入口无统一长度门禁 | 普通/兜底封存均可能绕过尺度 |
| L1 应服从计算预算，后级递减并熔断 | 只在提示词要求，解析器只接受字符串、计数，无预算及双熔断检查 | 名为多级压缩，实际可以是超长复述或重复层级 |
| 提取原文后剥离一次 | 重判按新 indices 返回，消费标记仍用旧 continuation_of；强制保存有全体+逐条两次封存 | 重复事件进入正式库 |
| 来源时间应随写入保留 | 批量构造 merged memory 时遗漏 occurred_at；逐句缓存缺时间归属 | 精确时间不能可靠传到事件和核心 |

## 正式第二轮量化检查

使用正式 manifest 的默认压缩/尺度参数，按每条原文长度重新计算预算：

- 共 94 个事件。
- 23 个原文长度达到或超过 1800 字符，超出本轮事件工作区间。
- 94 个事件的 L1 均超过程序为其计算的 L1 预算。
- 33 个事件的保存摘要中存在相邻层级不变短的情况。

这些数字按程序 `len` 的字符口径计算，与预算计算和召回计量一致。
英文输出的“字数”提示可能存在模型理解歧义，但不能因此把未校验的输出视为合规。
输入合并批量阈值约 3000 字符是评测回放设置；它不应取消生产内部分事件上限。

## 修复原则

1. 恢复一致的规则执行，而非围绕异常输出增加新策略。
2. 新版句子编号协议负责具体事件选择；长度规则仍须在其之后生效。
   不盲目把旧 80/20 分支接回新协议，避免丢失 source indices 与消费归属。
3. 所有最终封存入口共用长度、来源互斥与消费一致性检查；超过上限就拆分或明确待恢复，
   不以 truncated 标记绕过上限。保留待处理原文不等于发布成合规事件。
4. L1 校验预算，后级按前一级压缩并遵守已定双熔断；不要求无条件产满十级。
   格式合法不代表压缩合法。失败时保留源材料和错误，不默默发布成正常摘要。
5. 时间从原始发言跟随源片段传递，封存时间不能替代发生时间。

## 对已报告评测的解释

两轮数据仍能用于定位当前实现的问题，逐题回忆与回答是实际产生的。
但这些结果不能表述为“已经正确执行既定长度和压缩规则的匠石架构性能”。
先前只修改英文词面检索的试验改善了部分检索结果，没有修复上述规则偏差。
应先完成规则验收，再从空库重写、复测；当前不继续优化分数或更换模型以掩盖流程缺陷。
