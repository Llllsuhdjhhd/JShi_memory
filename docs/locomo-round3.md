# 第三轮：规则修复后的完整重写与评估

## 变更范围

本轮先修写入规则，再用同一组 LoCoMo conv-26 的 19 会话、419 条发言重新写入空库。
继续使用本地 BGE 英文嵌入和 deepseek-flash；30 题、答案条目文件、随机种子沿用前轮。
没有换模型，也没有用标准答案修正写入或检索结果。
所有完成版和失败尝试均保留，不能只选较好的一个展示。
`locomo_round3_v4` 为首个完成的规则修复版；后续验证版修改过度压缩。

- 新版句子编号分组之后执行长度约束，超长组按源句拆分；极长单句最后才按原字符分段。
- 重判、强制保存、物理红线改为源片段有界封存，取消整块加逐条的双重封存。
- 已认领源句不重复分配；同源、同原文重试复用事件，不把不同日期的相同表述合并。
- 摘要和对象事实按实际字符数验收；最终验证版 L1 无效时最多两次有界修复，仍失败即报错；
  后级不符合预算/递减/熔断就不发布，不截取句子冒充摘要。
- 逐段、逐句缓存保留来源时间和 IDs；源日期通过现有 JSON 元数据持久化并交付核心。
  多日期来源明确标为区间，不假装存在唯一相对时间锚点。
- 评测拒绝后端含 errors 的批次，避免不完整历史被自动计分。

## 与前轮的比较边界

本轮启用真实 JShi 默认投递触发条件（3000 字符、20 段、时间、夜间），
但同步提交以保持顺序确定，没有模拟后台处理期间的新经历积压。
数据集结束时提交剩余台账内容并强制封存残影，日志单列结束投递。
前两轮由回放器按约 3000 字符及会话末尾投递，因此变化不全来自某一个修复。
这仍是同批开发题，不是独立留出测试，也不是完整线上调度验收。

## 首个完成版的结果与暴露的问题

v4 的 30 题全部有效评分：正确率 36.67%，官方 F1 18.81%，充分信息覆盖率 50.69%
（自动原始结果，仍需结合理由复核）。相比前轮 50% 正确率出现退步。
其库内规则验收为：81 事件，最长原文 1797 字符，最长 L1 104 字符，
事件/摘要长度违规 0，同源重复 0，逐字原文重复 0，81 条均有时间与来源日期，
419 个原始发言来源标识全部覆盖，无残影遗留。
来源覆盖证明源标识进入事件，不等于每条语义事实都保留在摘要里。

抽读发现长度修复使用“只留一个主干事实”过度删减，造成生日的十年前、Bach/Mozart、
书籍类别等事实从摘要消失，有些摘要只剩寒暄。这里是本次修复策略的缺陷，不能归咎为检索未找到。

因此后续验证不改变预算、模型、题目或默认触发条件，改为修复调用输出排序后的简短完整事实，
优先保留具体人名、偏好、数字、时间、动作和结果，降低寒暄优先级；
程序在原 L1 预算内组装完整句子，不截断事实，不要求只保留一条，也不偷偷放宽字数。
所有 v4 结果与源码指纹保留，后续从空库重写验证。
v5 在 35 字符的图片描述处因模型未遵守长度被拒绝，未形成有效整轮结果。
v6 增加最后一次实际预算反馈，修复最多两次，最终完成整轮评测。

## 结论与下一步

已定位的重复封存、事件超长、摘要超预算、来源时间丢失在本轮库内得到修复，
但问答效果验收未通过。当前摘要选择仍会保留寒暄、丢弃具体人名和列表细节，
而检索只索引 L1/对象事实，被摘要删掉的关键词很难再找回。
事实列表组装满足了长度，却没有证明事实排序质量；不能把“压得短”当成“压得好”。

下一步应先做摘要关键事实保留校验，并审视英文按字符计算时的实际信息容量，
而非继续仅调检索权重或把全部问题归给最终回答模型。是否改变预算、事件粒度或摘要模型，
应作为明确的下一轮变量，不在本轮悄悄调整。
